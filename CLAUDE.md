# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Money Spending Board is a personal budgeting app (Supabase email/password + Google OAuth, editable/deletable transactions, editable 50/30/20 needs/savings/wants split, trend/compare spending charts, Thai/English i18n, PWA install + offline shell, client-side credit-card-statement PDF import) built on Next.js 16 App Router + TypeScript + Tailwind CSS, originally scaffolded from the [Next.js Boilerplate](https://github.com/ixartz/Next-js-Boilerplate) template. The home page (`app/page.tsx`) is the actual product; `about`/`blog` remain unmodified boilerplate placeholders (Lorem ipsum). `src/utils/AppConfig.ts` now carries real app metadata (no longer template-derived).

The app is statically exported (`output: 'export'` in `next.config.js`) — see `build-prod` below.

## Commands

```shell
npm install                 # install deps (Cypress's binary download is flaky in sandboxes;
                             # set CYPRESS_INSTALL_BINARY=0 to skip it if you don't need e2e)

npm run dev                 # dev server with live reload, http://localhost:3000

npm run lint                 # eslint . (legacy .eslintrc, NOT `next lint` — removed in Next 16)
npm run format                # eslint --fix + prettier on json/yaml
npm run check-types           # tsc --noEmit for both app and cypress tsconfigs

npm run test                  # jest (unit tests, colocated *.test.tsx)
npm run test -- Card.test    # run a single test file/pattern (standard jest CLI filtering)

npm run storybook             # Storybook dev server on :6006
npm run storybook:build       # build static storybook
npm run test-storybook:ci     # serve built storybook + run @storybook/test-runner against it

npm run cypress                # open Cypress interactively
npm run cypress:headless       # run Cypress headless
npm run e2e                    # start dev server + run Cypress (interactive)
npm run e2e:headless            # start dev server + run Cypress (headless) — used in CI with Percy

npm run build                  # scripts/set-sw-cache-version.js (bumps public/sw.js's cache name to
                                #   package.json's version) then next build -> static export in `out/`
npm run build-prod             # clean + build
npm run start                  # next start (production server mode)

npm run commit                  # Commitizen prompt for a Conventional Commit message
```

CI (`.github/workflows/CI.yml`) runs on Node 20 for: `build-prod`, commitlint (on PRs), `lint`, `check-types`, and `test`. There's no CI e2e or Storybook step — `e2e:headless`/Percy and `test-storybook:ci` are dropped from CI (vanity-engineering-review: the e2e step only ever exercised the stale Pages-Router boilerplate Cypress specs, and the Storybook test-runner only ever covered `Main.stories.tsx`, the sole `.stories.tsx` file and itself unmodified boilerplate — neither verified anything about the actual board product) and the build matrix is single-Node (dropped the second Node version — no bug had ever surfaced there); all of `npm run e2e`/`e2e:headless`/`storybook`/`test-storybook:ci` still work locally for optional manual use.

**ESLint stays on v8** (`eslint-config-airbnb`/`-typescript` have no flat-config release yet, and pairing them with ESLint 9+ means peer-dependency conflicts across the whole Airbnb/`@typescript-eslint` chain). `eslint-config-next` is deliberately pinned to `^15.5.9` rather than matching `next`'s major, since `eslint-config-next@16` requires ESLint 9+. Don't "helpfully" bump either without re-checking this — it's a known, considered pin, not drift.

## Architecture

- **Routing**: App Router under `app/`. `app/blog/[slug]/page.tsx` uses `generateStaticParams()` + async `params` (a `Promise`, per Next 16 convention) to statically generate `blog-0`..`blog-9`; `generateMetadata()` sets the per-slug title.
- **SEO/metadata**: no `next-seo` — every route exports `metadata` (or `generateMetadata`) directly, per the native Metadata API. `app/layout.tsx` sets the site-wide defaults from `AppConfig`; `app/sitemap.ts`/`app/robots.ts` (both need `export const dynamic = 'force-static'` for static export) replace the old `next-sitemap` dependency.
- **Site chrome**: `src/templates/Main.tsx` (header/nav/footer, pulls title from `AppConfig`) wraps `about`/`blog`, but **not** the board — `app/page.tsx` renders full-bleed since the board has its own self-contained header/UI that would clash with `Main`'s nav.
- **The board feature** (`app/page.tsx` → `BoardCard`):
  - `src/hooks/useSpendingBoard.ts` is a thin **orchestrator**, not a monolith — it composes the domain-sliced hooks below (each with its own colocated `*.test.ts`) and wires up the handful of cross-domain actions that touch more than one slice:
    - `useAuthSession` — Supabase session/boot state, email/password sign-in/sign-up, and OAuth sign-in. Creates the Supabase client (scoped to the `spending_board` db schema) from `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (see `.env.example`), read at build time; there is no in-app config UI, localStorage-based project override, or offline demo mode — if either var is missing it reports `configMissing` and the board renders a config-missing message instead of `AuthScreen`/the app. `NEXT_PUBLIC_SUPABASE_AUTH_PROVIDERS` (comma-separated, defaults to `google`) controls which "Continue with ___" OAuth buttons render; each provider must also be enabled in the Supabase dashboard.
    - `useTransactions`, `useImportCategoryRules`, `useBoardSettings` — the Supabase-backed slices (not localStorage): `useTransactions` loads/inserts/updates/deletes rows in `spending_board.transactions` (plus `bulkInsertTransactions` for the import flow below) and owns the add/edit transaction modal's open/form state (`AddTransactionModal` is reused for both add and edit — `editingTxId` set means edit); `useImportCategoryRules` owns the per-user merchant-keyword → category mapping in `spending_board.import_category_rules` (`guessCategory` matches the longest keyword contained in a description, defaulting to `wants`); `useBoardSettings` owns the single-row-per-user `spending_board.board_settings.badge_colors` JSON blob (the needs-review/source badge colors, user-editable in `ImportSettingsModal`).
    - `useCreditCardImport` — orchestrates the "pick a bank statement PDF → parse → preview → confirm" flow (`ImportStatus`: `idle → source → parsing → password? → preview`). It never talks to Supabase itself: it calls `extractPdfText` + a source's `parse` fn (from the `IMPORT_SOURCES` registry it also owns) to get rows, `useImportCategoryRules.guessCategory` to pre-fill each row's category, flags likely duplicates against already-loaded transactions (same `date`+`amount`, only against rows that themselves have a `source` set), and on confirm calls `useTransactions.bulkInsertTransactions` (threaded in by the composition root). See `openspec/changes/2026-08-23-import-ktc-credit-card-statement/design.md` for the numbered decisions referenced throughout this code (e.g. "Decision 2" = one hardcoded bank parser today, still behind a real source-picker registry so a second bank is additive).
    - `useRatios`, `useProfile`, `useCategoryMeta` — each persists to `localStorage` under a key namespaced by the signed-in email (`msb_ratios_<email>`, `msb_profile_<email>`, `msb_catmeta_<email>`); there's no server sync for these, only per-browser persistence.
    - `useI18n`, `useTheme` — language (`th`/`en`) and light/dark theme, no persistence beyond component state.
    - `useOnlineStatus` — wraps the browser's `online`/`offline` events, no persistence. The board's Supabase-backed mutations (add/edit/delete transaction) are disabled with an `offlineBanner` message whenever `isOnline` is `false` — there's no offline write queue, only the read-only cached shell described below.
    - `useSpendingBoard` itself composes a few actions that cross slice boundaries (e.g. `editSplitFromProfile` closes the profile modal and opens the ratio modal; `openCategorySettings`/`openImportSettings`/`startImport` do the same for category settings, import settings, and the import flow) and derives view-ready data other hooks can't own alone: `categoryCards`, `transactionRows` (also threads `needsReview`/`sourceLabel` from `useTransactions` and `badgeColors` from `useBoardSettings`), `monthlyTotals` (per-month income/expense/category breakdown, feeds the Trend chart), `compareRows` (selected vs. previous month per category, feeds the Compare chart).
  - `src/components/board/*` — presentational components, each typed via `Pick<ReturnType<typeof useSpendingBoard>, ...>` rather than duplicating prop types: `BoardCard` (top-level composer), `AuthScreen`, `BoardHeader`, `BoardTabs` (Overview/Graph tab switcher, and the nested Trend/Compare switcher), `BudgetSplit`, `TransactionList` (also renders the needs-review/source badges and the "All"/"Needs review" filter), `TrendChart` (stacked horizontal bars) and `CompareChart` (grouped vertical bars, self-contained — inlines its own bar-geometry rendering rather than sharing a primitive with `TrendChart`, since their layouts never converged and a shared abstraction had only one real consumer), and six modals: `AddTransactionModal`, `CategorySettingsModal`, `ProfileModal` (also the entry point for "Import from PDF"), `RatioModal`, `ImportPreviewModal` (source picker → password prompt → editable preview table steps), `ImportSettingsModal` (import-rule CRUD + badge color pickers). Static/structural styling is Tailwind; genuinely dynamic per-theme/per-category colors are inline `style` (can't be static Tailwind classes since they're runtime-computed). None of these have colocated component tests/stories yet (only the hooks and `boardHelpers` do) — don't take that as precedent for skipping tests on other new components.
  - `src/utils/BoardConfig.ts` — all constants: category groups, icon SVG paths, color palette, and the full Thai/English `I18N` dictionary. `src/utils/boardHelpers.ts` — pure helpers (`fmtMoney`, `themeTokens`, `monthKey`, `previousMonthKey`, etc.). `src/utils/importParsers/` — pure, no-I/O parsing: `extractPdfText.ts` (client-side PDF text extraction via `pdfjs-dist`'s `legacy/` build, dynamically imported only when the import flow is opened; reconstructs lines by grouping text runs whose baseline Y position is within `Y_TOLERANCE`, since `getTextContent()` returns no inherent line breaks; also owns the password-protected-PDF retry loop via an `onPassword` callback) and `ktc.ts` (`parseKtcStatement` — KTC credit-card-statement-specific line parsing; the only entry in the `IMPORT_SOURCES` registry today).
  - `next/font/google` (Manrope + Inter) is loaded in `app/page.tsx` and scoped to the board via Tailwind's `font-manrope`/`font-sans` (see `tailwind.config.js`), deliberately *not* changing the site-wide font (`global.css` still sets IBM Plex Sans Thai globally for `about`/`blog`).
- **PWA / offline shell**: `app/manifest.ts` (`export const dynamic = 'force-static'`, like `sitemap.ts`/`robots.ts`) generates `/manifest.webmanifest`, linked from `app/layout.tsx`'s `metadata.manifest` plus `appleWebApp`/icon metadata. `src/components/ServiceWorkerRegistration.tsx` (rendered in `app/layout.tsx`, above `children`) registers `public/sw.js` **only in production** (`canRegisterServiceWorker` gates on `NODE_ENV === 'production'`, so dev builds never install one) and shows a fixed-position "reload" banner when a *second* `controllerchange` event fires — the first one just means the tab came under SW control for the first time, not that a new version replaced an old one. `public/sw.js` precaches a fixed shell (`/`, the manifest, icons, `offline.html`) on `install`, serves navigations network-first falling back to `caches.match('/offline.html')` when the network genuinely fails (`cache: 'no-store'`, not the browser's HTTP cache), serves everything else cache-first, and never intercepts cross-origin requests (Supabase calls always hit the network). `scripts/set-sw-cache-version.js` rewrites `sw.js`'s `CACHE_NAME` constant to `msb-shell-v<package.json version>` as part of `npm run build` — don't hand-edit that line, it's overwritten on every build, and it's what makes the `activate` handler evict the previous version's cache.
- **Supabase schema** (`supabase/migrations/*.sql`): the `transactions` table lives in a dedicated `spending_board` schema (moved off `public` — see the schema-move migration's comment for why `ALTER ... SET SCHEMA` was used instead of drop/recreate: it preserves data/indexes/RLS on a database with real rows). `transactions` also carries `source text` (e.g. `'ktc_import'`, set only by the import flow, left untouched by manual edits) and `needs_review boolean not null default false` (set `true` on as-imported rows the user hasn't touched yet, cleared on any edit through `AddTransactionModal`). `spending_board.import_category_rules` and `spending_board.board_settings` (see above) round out the schema. RLS policies scope every row to `(select auth.uid()) = user_id` — wrap `auth.uid()` in a scalar subquery (not a bare call) so Postgres evaluates it once per statement, not once per row (the `auth_rls_initplan` advisor warning). Since `auto_expose_new_tables` defaults to `false`, the Data API roles (`anon`/`authenticated`/`service_role`) also need explicit `grant`s on the table itself — RLS alone doesn't expose it. Run new migrations through the Supabase MCP tools or CLI, not by hand-editing the remote database.
- **Path aliases** (`tsconfig.json`): `@/*` → `src/*`, `@/public/*` → `public/*`, `@/lib/*` → `lib/*`, `@/translations/*` → `translations/*`. Only the first two are mirrored in `jest.config.js`'s `moduleNameMapper` and only the first two directories (`src/`, `public/`) actually exist — `lib/` and `translations/` are reserved but unused, so add their `jest.config.js` mapping if code ever lands there. Always import via `@/...` for cross-directory imports.
- **Tests are colocated** directly next to what they test — including routes, e.g. `app/about/page.test.tsx` tests `app/about/page.tsx`. This works because App Router only treats reserved filenames (`page`, `layout`, `route`, etc.) as routes, unlike the old Pages Router where anything under `src/pages/` was magic; there's no more `pages.test/` workaround directory.
- **Styling**: Tailwind CSS v3. `tailwind.config.js` extends the default spacing scale with half-steps (`4.5`–`9.5`) that the board's components rely on — if you add a new fractional spacing class, make sure it's either in that extension or a default Tailwind value, since silently-unmatched classes (e.g. a stray `pb-25`) generate no CSS at all. `content` covers both `src/**` and `app/**`.
- **Storybook**: stories are colocated (`*.stories.tsx`, e.g. `Main.stories.tsx` — still the only one). Storybook 10 — `@storybook/addon-essentials`/`-interactions`/`@storybook/testing-library` were folded into core; use `storybook/test` for interaction-testing utilities (`userEvent`, `within`), not the old separate packages. No longer run in CI (dropped for testing only unmodified boilerplate — see the CI note above); `npm run storybook`/`storybook:build`/`test-storybook:ci` still work locally.
- **E2E**: Cypress specs in `cypress/e2e/*.cy.ts` predate the board feature and assert against the old Pages Router boilerplate content — treat them as known-stale, not a regression bar, until someone rewrites them for the current app. No longer run in CI (dropped for testing boilerplate instead of the product); `npm run e2e`/`e2e:headless` still work locally if you want to run them manually.
- **Feature workflow (OpenSpec)**: non-trivial features go through `openspec/` — a change proposal (`openspec/changes/<date>-<slug>/proposal.md`, `design.md`, `tasks.md`) plus delta specs, synced into `openspec/specs/<capability>/spec.md` and archived to `openspec/changes/archive/` once shipped (see e.g. `2026-07-27-add-spending-graphs`, `2026-07-25-split-spending-board-hook`). Use the `openspec-*`/`opsx:*` skills for this rather than hand-rolling the structure — `DEVELOPER.md` documents the full explore → propose → apply → verify → sync → archive → `/to-spec` loop, including how OpenSpec (in-repo, drives the build) and the separate Matt Pocock `to-spec`/`implement` skills (publishes the finished result to a GitHub Issue) fit together. `2026-08-23-import-ktc-credit-card-statement` (the credit-card-import feature above) is still an **active, unarchived** change — its tasks are done but it hasn't been through `/opsx:sync`/`/opsx:archive` yet, so don't be surprised there's no matching capability under `openspec/specs/` for it yet. CI (`.github/workflows/CI.yml`) ignores `openspec/**`-only pushes/PRs (`paths-ignore`), so pure spec/doc changes don't trigger the build/test matrix.

## Conventions

- **Commits**: enforced [Conventional Commits](https://www.conventionalcommits.org/) via commitlint (validated in CI on PRs); use `npm run commit` for the guided Commitizen flow. Releases are automated with `semantic-release` on `develop` — the repo's actual default/production branch (there is no `main`).
- **ESLint** (`.eslintrc`, legacy format — see the pin note above): Airbnb + Airbnb TypeScript + `next/core-web-vitals` + Tailwind + Prettier, with project-specific overrides worth knowing:
  - `simple-import-sort` is enforced — imports/exports must be sorted; let `npm run format` fix this rather than hand-ordering.
  - `unused-imports/no-unused-imports` is an error; unused vars prefixed with `_` are allowed.
  - `@typescript-eslint/consistent-type-imports` is enforced — use `import type { X }` for type-only imports.
  - `import/prefer-default-export` is off — prefer named exports, except Next.js `page.tsx`/`layout.tsx` files which require `export default`.
  - `react/jsx-props-no-spreading` and `react/require-default-props` are off.
  - `jsx-a11y/label-has-associated-control` and `jsx-a11y/control-has-associated-label` are enforced — every `<label>` needs a matching `htmlFor`/`id` pair (or use a plain `<div>` if it's a group heading, not a real form label), and icon-only buttons need `aria-label`.
- **TypeScript**: strict mode is on (`strict`, `noUncheckedIndexedAccess`, `noUnusedLocals`, `noUnusedParameters`, etc.) — `npm run check-types` must stay clean. `moduleResolution: "bundler"` (required for modern `exports`-map packages like Storybook 10); `target: "es2017"`.
- Component prop types use the `I`-prefixed interface/type naming convention in the original boilerplate files (`ICard`, `IMainProps`); the board's newer files instead derive prop types from the hook's return shape (`Pick<ReturnType<typeof useSpendingBoard>, 'foo' | 'bar'>`) rather than hand-duplicating them — follow whichever convention matches the file you're in.
- Function components are typically defined and exported inline as `export const X = (props) => (...)` (not `export default`), except Next.js route files which require `export default`. (`src/templates/Main.tsx`, one of the few surviving boilerplate files, instead defines then exports via a trailing `export { Main }` — that's the outlier, not the pattern to copy for new components.)
